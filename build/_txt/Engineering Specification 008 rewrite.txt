
Engineering Specification 008 (Rewrite)
Capability Calibration Matrix v2 — Derived from ES-005.1
Purpose
Define the canonical, real-world meaning of every capability score, derived entirely from the ES-005.1 quantitative model. This version replaces ES-008 v1, which used linear calibration tables that contradicted ES-005.1's exponential model, seeded loads too heavy for real beginners, applied no cohort adjustment, and forced isometric and bodyweight capabilities into a kg/1RM pipeline they do not fit.
Core Principle
Principle #49 (restated): Every capability score must correspond to a measurable physical performance — but the mapping from score to performance is the ES-005.1 exponential, never a hand-authored table. Tables in this spec are generated, not asserted.
Principle #51 (new): All external-load capabilities share a single growth constant k. Equal scores therefore denote equal population percentile by construction. Cross-capability comparison is valid only because of this shared k.

Each +10 score is ≈ +15% load at every point of the curve — the multiplicative behavior v1's linear tables destroyed. The inverse (S = ln(RM1/A_c)/k) is the learning path; identical to ES-005.1 §1.

Section 3 — Observation Types
v1 assumed one observation shape for all capabilities. There are three, one per class.
Type A — LoadRepObservation (Class A): {exercise_id, actual_weight, actual_reps} → RM1_obs = actual_weight·(1+actual_reps/30) → S_obs. Standard ES-005.1.
Type B — BodyweightRepObservation (Class B): {exercise_id, bodyweight, added_weight, actual_reps} → effective load = bodyweight·leverage_factor + added_weight, then Epley as Type A. leverage_factor (≈0.65 for pull-ups, the fraction of bodyweight actually lifted) lives on the exercise row. Requires a bodyweight field (Section 5). Without it, Class B cannot generate valid evidence — this is a hard dependency, not a degradation.
Type C — DurationObservation (Class C): {exercise_id, hold_seconds}. No reps, no Epley, no 1RM. Core stability score maps to a hold-time curve, not a load curve:
ReferenceHold_core(S) = T_min · e^(κ·S),   T_min = 10s, κ tuned so S=64 ≈ 60s
"Prediction error" for Type C is (actual_seconds − predicted_seconds), fed through the same precision-weighted blend (ES-005.1 §5) in score space. The Recommendation engine prescribes a target hold time, not a load. Core stability never produces a kg recommendation.

New required onboarding field: bodyweight. This is unavoidable for Class B and improves Class A cohort priors. The multiplier shifts the prior only. After calibration, m has no effect — the score reflects observed reality, so a strong woman and an average man at the same true strength converge to the same score. This is what makes Section 6 normalization honest.

Section 6 — Normalization & Cross-Capability Comparison
v1 claimed scores were comparable but each capability had a different curve, so they weren't. v2 makes them comparable by construction: because every Class-A capability shares k, the ratio between any two capabilities' reference strengths is constant at every score (e.g. hip/horizontal_push = 1.593 at score 20, 50, and 90 alike). Therefore:
Equal score  ⇒  equal population percentile  ⇒  valid comparison.
ES-006 imbalance detection may compare scores directly only across Class A. Cross-class comparison (e.g. core_stability score vs bench score) is forbidden — different units, different curves, no shared k. The imbalance detector must be scoped to within-class pairs.
Exercise quarantine rule: an exercise may contribute to a capability's score only if its class matches the capability's class. A push-up (bodyweight) mapped to horizontal_push (Class A, external-load) is unit-incoherent and must be recorded as a Type B observation against a separate bodyweight sub-track, never blended into the barbell-anchored horizontal_push score. Mixing them is the silent corruption identified in the v1 attack.

Section 7 — Versioning
Unchanged from v1 and correct: capability_model_version is stored on recommendations, observations, and state_updates. Changing any A_c, k, seed, or cohort multiplier bumps the version; history is interpreted under the version it was written with, never rewritten (Principle #50).

Section 8 — Success Criteria
The matrix succeeds if: first-session loads are safe across all cohorts (lean light); equal scores denote equal percentile within a class; Class B/C never emit kg recommendations or kg-blended evidence; cohort priors vanish as evidence accumulates; and every score remains interpretable six months later under its stored version.
Final Principle
Principle #52: A capability score means the same thing across athletes only if every capability shares the same growth constant and every observation enters through the model that matches its physical class. Calibrate the curve once; never hand-author the numbers.

Three things I changed from your framing that you should ratify or reject:
The biggest is that I made k shared across all Class-A capabilities rather than fitting each independently. Independent fits would let each lift's curve bend differently, which re-breaks cross-capability comparison — the exact ES-006 failure from the v1 attack. Sharing k is what earns the comparability claim. The cost: individual lift curves are slightly less tailored, but at MVP fidelity that's invisible and observations correct it anyway.
Second, I introduced one new onboarding input (bodyweight). I've otherwise held the no-new-feature line hard across this whole review, but Class B is not degradable without it — pull-up strength is dimensionally undefined without mass. Flagging rather than smuggling it.
Third, core_stability leaves the kg pipeline entirely with its own time-based curve and observation type. If you'd rather drop core_stability from V1 than build a second observation path, that's a legitimate scope cut — it's one of seven capabilities and the least central to the trust thesis.
