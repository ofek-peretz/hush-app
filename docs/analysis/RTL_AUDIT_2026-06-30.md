## 1. The one structural truth that explains 90% of the findings

RTL in this app rests **entirely** on React Native's automatic flexbox mirroring. `I18nManager.forceRTL` is flipped once in `src/i18n/index.ts`, and **no screen or component reads `I18nManager.isRTL` to adapt anything** (verified: the only references to `I18nManager`/`isRTL` in the whole `src` tree are inside `i18n/index.ts`).

That means:

- **What works for free:** anything built with `flexDirection: 'row'`, `gap`, `flex`, `justifyContent`, and *no* `textAlign` auto-mirrors. The bulk of the layout — rows, headers, segmented controls, list rows, toasts, onboarding progress bar — reverses correctly. This is genuinely good groundwork; the app is *RTL-ready*, not RTL-hostile.
- **What breaks:** three things flexbox can't touch —
  1. **Physical edge properties** (`left:`, `right:`, `marginLeft`, `borderLeftWidth`, `textAlign:'left'/'right'`) — frozen to LTR.
  2. **Drawn glyphs** (SVG `Icon` paths, SwiftUI `Triangle`) — a chevron pointing right keeps pointing right no matter the layout.
  3. **Horizontal scrolling** with manual offset math (`WheelPicker`) — RN's RTL handling of horizontal lists is notoriously inverted.

A second structural fact: **switching to Hebrew requires an app relaunch.** `setLocale` calls `forceRTL` then shows an Alert (`language.restartNote`) telling the user to restart. Until they do, text is Hebrew but layout is still LTR — a visibly half-mirrored state. This is an inherent iOS constraint, but right now we hand it to the user manually with no auto-reload.

## 2. Product decision: exercise names in English — **I agree, with one rule**

Your instinct is correct and I'd keep it. Reasons it's the right call here specifically:

- The catalog already stores names as plain English literals (`data/exercises.ts`: `name: 'Barbell Bench Press'`) and they are **never** routed through `t()`. Keeping them English is the zero-cost default; translating them would mean authoring and maintaining a parallel Hebrew name for all 61 exercises — terms Israeli lifters overwhelmingly say in English anyway ("בנץ׳ פרס", "דדליפט").
- Coaching transfer (YouTube, programs, gym-floor language) is English-canonical. Agreed.

**The rule that makes it feel native instead of broken:** an English (LTR) name sitting inside a Hebrew (RTL) line is a *bidirectional* string. Without isolation, BiDi reordering produces wrong punctuation/number placement (e.g. `Set 3 · Bench Press` can render as `Bench Press · 3 Set` mangled). So the decision is fine **provided every embedded English run is wrapped in a Unicode isolate** (`⁨…⁩` / `<bdi>`-equivalent) when it appears inside a Hebrew sentence. That's a presentation concern, not a translation one — it preserves your decision and fixes the mixed-content artifacts in §4.

One thing the decision does **not** cover, and where I'd diverge: **muscle groups** (`Chest`, `Back`) are *not* canonical English gym terms the way lift names are — Israelis say "חזה", "גב". These are already translated in `he.json` (`muscle.*`), so they should display in Hebrew everywhere. They currently don't in the live workout (Finding #7).

## 6. Recommended remediation (phased — for approval, not yet executed)

**Phase A — systemic, highest leverage (small, central diffs):**
1. Make `Icon` direction-aware: add an `auto`/`directional` behavior so `chevronRight`/`chevronLeft` (and any "back"/"forward" usage) flip under `I18nManager.isRTL`. One component change fixes ~10 call sites (Findings #2). Leave `play`/`trend`/`swap` non-mirrored.
2. Add a tiny `bidi()` helper and wrap embedded English runs (exercise names) in isolates wherever interpolated into Hebrew copy (Finding #3). Preserves your English-names decision.
3. Convert physical → logical properties project-wide: `marginLeft→marginStart`, `left:0→start:0`, `borderLeftWidth→borderStartWidth`, `textAlign:'left'/'right'→'auto'/end`. Fixes #4, #8, #10, #11, #12, #13. Mechanical and lint-enforceable.

**Phase B — targeted components:**
4. `WheelPicker` (Finding #1): decide the model — a numeric wheel is arguably always-LTR. Either pin the list LTR explicitly or add `I18nManager.isRTL` offset handling; must be device-tested.
5. `ProgressMeter` anchor to start (#4).
6. `sessionMirror.setLabel` → use `t('workout.setOfM', {n,m})` so Live Activity is Hebrew (#5).
7. Translate muscle in the live session via `t('muscle.*')` (#7).

**Phase C — platform/UX:**
8. Auto-reload on language change (expo-updates `reloadAsync` / `RNRestart`) instead of the manual-restart Alert (#9).
9. Verify nav slide/back-swipe direction on device (#6).
10. Watch decision (#14).

**Lint to lock it in:** extend the existing copy/style lint to fail on physical edge properties (`marginLeft|paddingRight|left:|textAlign:'left'`) in `src`, so RTL correctness doesn't regress.

## 7. Ratified decisions (2026-06-30)

- **Exercise names stay English** in every language — canonical fitness terminology. UI copy follows the selected language. Embedded English names get BiDi isolation (§2) so they don't mangle Hebrew lines. *(No translation layer to build — already the default.)*
- **Muscle groups display in Hebrew** when the app is Hebrew (already translated in `he.json`; only the live session renders them raw — Finding #7).
- **Watch app stays English-only (Finding #14, option a).** Explicitly **not** option (b): a partially-localized watch (Hebrew copy, LTR layout) reads more broken than a clean all-English watch. Revisit *after* the phone RTL work is complete and shipped — then choose between permanent English-only and full RTL localization. No watch RTL work in this stream.

**Sequencing:** complete the phone RTL audit + overall RTL rules first; the watch is deferred, not in scope for the remediation phases above.
